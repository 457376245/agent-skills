# 审查清单

执行 Requirement Doc Review 时，用这份清单约束审查范围。目标是判断“当前代码是否满足需求实施追踪文档”，不是做泛泛的代码美化。

## 输入完整性

- 是否找到了唯一明确的需求实施追踪文档？
- 文档是否包含原始需求、范围边界、假设和验收标准？
- 文档是否包含最终一致性检查或阶段性交接说明？
- 文档是否记录实际验证结果和未验证事项？
- 文档是否声明了准确的审查目标：提交 SHA、PR 及其 head SHA，或未提交工作区及当前 HEAD SHA？

## 审查快照

- `git rev-parse HEAD` 是否与声明的审查目标一致？
- `git status` 的干净或未提交状态是否与文档声明一致？
- 需要限定 diff 时，是否提供了可核对的实现基线？
- 多仓库需求是否逐仓库记录并核对了审查目标？
- 目标缺失、含糊或不匹配时，是否已停止且未设置 `审查中`，并交回 `requirement-doc-tracking` 写入准确快照，而不是接受笼统口头确认或静默审查当前代码？
- 非 Git 工作区是否有用户提供的不可变制品标识？没有时应判定为 `无法确认`。

## 需求达标

- 每条验收标准是否能在代码、测试、配置或文档中找到证据？
- 是否存在文档说已交付但代码没有实现的行为？
- 是否存在代码实现超出范围，且文档未说明的行为？
- 是否存在本次明确“不做”的内容被误实现或被实现依赖？

## 技术一致性

- 文档列出的文件、模块、接口、路由、表、配置、任务是否真实存在并被正确修改？
- 代码中实际修改的关键文件是否已记录在文档中？
- 接口、数据库、权限、状态流转、定时任务、MQ、缓存等影响是否与文档一致？
- 跨项目或外部依赖是否记录了真实契约和依赖顺序？

## 验证可靠性

- 已运行测试是否覆盖核心验收标准？
- 未运行测试是否有明确原因？
- 是否存在只能通过人工、环境或外部系统确认的事项？如果有，标记为 `无法确认`。
- 是否有必要补充单元测试、集成测试、接口测试或手工验证步骤？

## 报告要求

- 结论先行，阻塞问题优先。
- 每个问题尽量引用文件、行号、测试、命令结果或文档章节。
- 区分 `不通过`、`部分通过`、`无法确认`，不要把未知事项写成通过。
- 不直接修改业务代码，除非用户明确要求修复。
- 只回写审查状态、最近审查结论、最近审查时间和报告路径，不修改实施状态。
- 整改期间是否保持上一轮 `已审查` 状态和结论，并仅在整改完成、由 `requirement-doc-tracking` 重新对齐实施事实、验证记录和审查目标后设为 `待审查`？
- 需要同步其他追踪内容时，在报告里提出并交回实施流程。
